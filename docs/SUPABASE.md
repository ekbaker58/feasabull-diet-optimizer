# Supabase setup

Supabase stores the optimizer's data so prices and foods can change without touching code, and lets
signed-in users save their plans.

## What's in `supabase/`
| File | What it does |
|---|---|
| `config.toml` | Generated by the official Supabase CLI (`supabase init`, v2.40.7). Needed by the GitHub integration. |
| `migrations/20261026193000_diet_optimizer_schema.sql` | Tables `foods`, `diets`, `group_caps`, `optimizer_settings`, `saved_plans`; row level security; `updated_at` trigger |
| `migrations/20261026193100_seed_diet_data.sql` | The 71 foods, 8 diets, 6 group caps and default settings, as **upserts** (safe to run again) |

`foods.cost_per_100g` is a **generated column**: price ÷ (package grams × edible yield) × 100. Edit the
price and the cost updates itself.

## Who can do what (row level security)
| Table | Anyone (anon key) | Signed-in user | Dashboard / service role |
|---|---|---|---|
| foods, diets, group_caps, optimizer_settings | read | read | read + write |
| saved_plans | nothing | read, save, delete **their own** rows only | everything |

These rules were tested on Postgres 16 with the migrations applied twice:
- Anonymous users can read all 71 foods but cannot change a price or save a plan.
- A user can save a plan, cannot save one as someone else, and cannot see another user's plans.

## How the migrations get to your database
- **GitHub integration with Branching on:** a pull request that touches `supabase/` gets a **preview branch**
  database (separate from production) where these migrations run. Check it there first.
- **Merging into the production branch** (`main`) applies them to production **if** "Deploy to production"
  is enabled in the integration settings. Check that setting before merging.
- **Or by hand:** `npx supabase login`, `npx supabase link --project-ref <your-ref>`, `npx supabase db push`.
- `config.toml` says Postgres 17 (the default for new projects). If your project runs 15, change `[db] major_version`.

**Before merging:** if your project already has tables named `foods`, `diets`, `group_caps`,
`optimizer_settings` or `saved_plans`, rename them here first. The migrations use `create table if not exists`,
so a table that already exists with different columns will be left as it is, and the data step will then fail.

## Using it from the website
```js
import { createClient } from "@supabase/supabase-js";
import { optimizeDiet } from "./lib/dietOptimizer.js";
import { loadOptimizerData, savePlan, listPlans } from "./lib/supabaseData.js";

const supabase = createClient(import.meta.env.VITE_SUPABASE_URL, import.meta.env.VITE_SUPABASE_ANON_KEY);
const data = await loadOptimizerData(supabase);                 // live foods, diets, caps, settings
const result = optimizeDiet(targets, { diet: "Balanced", data });
await savePlan(supabase, { targets, prefs: { diet: "Balanced" }, result });   // signed-in users only
```
Only the **anon (publishable) key** goes in the website. Never put the service-role key in front-end code or in this repo.

Checked: running the optimizer on rows read back from Postgres gives the same cost as the built-in data
for all 8 diets (largest difference $0.000003/day). Lowering a price in the table changes the plan.

## Changing data
- **One price, quickly:** edit the row in the Supabase Table Editor. The site picks it up on the next load.
  The spreadsheet and the built-in fallback won't know, though.
- **The proper way (keeps everything in sync):** edit `config/diets.json` (diets) or `scripts/foods_v2.py`
  (foods, prices) and push. GitHub Actions regenerates the JSON, the optimizer, the page, the workbook and
  `20261026193100_seed_diet_data.sql`.
- **Getting that change into a database that already exists:** Supabase applies each migration file only once,
  so a regenerated seed file does **not** update a live database. When you want the database updated, run
  `python scripts/build_supabase.py --release`. It writes a new `<timestamp>_update_diet_data.sql` with the
  same upserts (safe to re-run). Commit it and merge; the integration applies it like any migration.
- **Deleting is manual:** removing a diet or food from the source files doesn't delete its row (saved plans may
  still reference a diet by name). Delete it in the Table Editor if you need to.
